# Craps comps — build plan

Status: BUILT in the working tree on 2026-09-05, uncommitted, awaiting review. Supersedes sections 2 and 3 of
`CRAPS-VAULT-COMP-BUDGET-PLAN.md`; that document's accrual formula (section 1) and acceptance
tests (section 5) carry over unchanged and are referenced below rather than restated.
Source reviewed: `e013043d9`, clean tree, 2026-09-04.

## Locked decisions

- Granular comps: the vault owner can seat a named recipient in one of today's scheduled
  windows, today's whole day, a run of future days, upgrade a recipient's day ticket to the
  high lane, and bank pass credits. Custom battles are not compable (user ruling, 2026-09-05).
- Dedicated lane. The comp budget is a separate FLIP-wei allowance in FLIP, not the vault's
  general mint allowance, so it can never become spendable FLIP through the redemption path.
- Accrual: 2% of eligible bankroll per completed battle, credited once at finalization, exactly
  as the earlier plan's section 1 defines it.
- The 200-pass lifetime allowance converts to the lane's initial value: 4,560,000 FLIP.
- Space comes from relocating the pure dice engine, not from a payout module.

## Phase A — relocate the dice engine (no economic change)

### A1. `contracts/CrapsEngine.sol`

`contract CrapsEngine is Craps` with one external pure function. Take the packed chip word
and the scatter hash, not the built board, so the board never crosses the boundary:

```
function settleSlip(
    uint256 packedChips,   // the slip's chip word, already vetted by _packChips
    uint256 chipFlip,      // per-chip stake in FLIP
    uint256 scatterHash,   // _hash2(word, player) — the caller's existing scatter seed
    bytes32 seed,          // _crapsSeed(word, bound)
    uint256 bankroll,
    uint256 goal,
    address player,
    uint256 boost
) external pure returns (SlipResult memory);
```

Inside: `_boardFrom`, `_scatterInto`, then `_settleSlip` with the table's fixed
`_MAX_SLIP_HANDS` and `_SLIP_ROLL_BUDGET`. Move `_boardFrom` and `_scatterInto` down into
the `Craps` base so the engine and the table compile the same source; each has exactly one
caller today, so nothing else in the table references them after the move.

The engine holds no storage, no constructor arguments, no owner and no upgrade path. It is a
pure function at a pinned address, reached by STATICCALL.

### A2. CrapsBattle

- Declare `ICrapsEngine` beside the other interfaces at the top of the file.
- `_settlementOf` builds the arguments it already has and calls
  `ICrapsEngine(ContractAddresses.CRAPS_ENGINE).settleSlip(...)`. Bare call, no gas stipend,
  no try: a pure callee at a pinned address has no failure mode to defend against.
- `_settlementOf` changes from `pure` to `view` (an external call is not allowed in pure).
  `previewSettlement` is already `view`; `_resolve` is state-changing. No other caller.
- `_packChips` stays in the table: the entry doors validate through it and `_settlementOf`
  still needs `placed` for the shooter boost terms.
- Retune the size gate in `test/craps/CrapsGas.t.sol` (currently `<= 24,400`) to a figure
  that guards the new headroom instead of the old one.

### A3. Deployment and pins

- `scripts/lib/predictAddresses.js`: append `CRAPS_ENGINE` as N+30, mapped to `CrapsEngine`.
  Appending shifts no existing address.
- `contracts/ContractAddresses.sol`: new `CRAPS_ENGINE` constant (regenerated by the patch
  scripts, as every other constant is).
- `scripts/deploy.js`, `scripts/deploy-local.js`, `test/helpers/deployFixture.js`: deploy the
  engine at that nonce. `test/craps/CrapsPins.sol` `_installPins`: etch the engine at the
  pinned address for every Foundry craps suite.
- `scripts/bytecode-manifest.sh`: add `CrapsEngine` to `CONTRACTS` (and note `CrapsBattle`
  was never in that list; add it in the same edit).
- `scripts/check-interface-coverage.sh` must see the new interface; ABI union generation and
  source bundling pick up the new file.

### A4. Gates for Phase A

- Differential parity: a test contract `is Craps` that still compiles the inline engine, fuzzed
  over chip words, seeds, bankrolls, goals and boosts, asserting the engine returns an identical
  `SlipResult`. This is the proof that relocation changed nothing.
- Every craps suite green. Every existing `CrapsGas` threshold still holds without retuning
  except the size gate.
- `bash scripts/layout/storage_layout_oracle.sh`: no storage change, run it anyway.
- Slither over the new contract; the `check-delegatecall` and `check-raw-selectors` gates
  (the engine call is a typed interface call, not a raw selector).
- Report the final CrapsBattle and CrapsEngine sizes and the cold and warm per-seat gas.

## Phase B — the dedicated comp lane in FLIP

### B1. Storage

`uint128 crapsCompAllowance = 4_560_000 ether;` declared immediately after
`_tombstoneFlooded`. That slot holds one bool today, so the field lands in its free bytes
and shifts nothing. Declaration-time initializer only: no setter, refill or reset.

### B2. Spending: one flag bit in the craps burn

- New `CRAPS_FLAG_COMP = 0x10` inside the existing low-byte flag mask.
- In `burnCoinForCraps`, when the flag is set: require `msg.sender == CRAPS` (already the
  gate), debit `crapsCompAllowance` by `gross` or revert `Insufficient`, emit
  `CrapsCompSpent(player, gross)`, return a zero boon mask. Skip the shortfall consume, the
  burn, the boon consume and the quest report entirely. `player` is the recipient, for the log.
- Nothing else in FLIP changes. The paid path is byte-for-byte the same statement sequence.

### B3. Accrual door

`creditCrapsComps(uint256 amount)`, CRAPS-only, adds to the lane and emits
`CrapsCompsAccrued(amount, balance)`. A public view `crapsCompAllowance()`.

### B4. Invariants (tests)

- The lane never enters `totalSupply`, `supplyIncUncirculated`, `balanceOf(VAULT)` or the
  vault mint allowance; `vaultMintTo` cannot draw on it; `vaultEscrow` cannot feed it.
- Only CRAPS can debit or credit it. A comp burn with the flag from any other caller reverts.
- The initial figure is 4,560,000 FLIP and no public call resets it.

## Phase C — accrual at finalization (CrapsBattle)

In `_payout`, after the finalization log and outside the `scheduled` branch, so a custom
battle with zero bounty still earns:

```
N = entrants                       (g & _MASK32, day seats already folded in)
K = uint32(_highField[w.key])      (this window's high seats, day upgrades already folded in)
B = uint256(w.bankroll)
eligible = B * N + (K != 0 ? B * K * (w.highMult - 1) : 0)
earned   = eligible / 50
if (earned != 0) IFlipCoin(ContractAddresses.COIN).creditCrapsComps(earned)
```

- Read K before the `_HF_DONE_BIT` write or after; the counter sits in the low 32 bits and the
  done bit at 169, so either order reads the same count.
- The sole-high extra bounty capital stays out, as the earlier plan's section 1 requires.
- Bump the deterministic settlement work reserve by the cost of one cold external call plus one
  warm SSTORE and one log. The reserve is a constant, never `gasleft`.
- Tests: the earlier plan's accrual oracle and partition-independence cases, verbatim.

## Phase D — comp doors on the table, owner door on the vault

### D1. Thread the player through the private doors

`msg.sender` currently names the seat owner in `_place`, `_enterDayLane`, `_reserveRun`
and `upgradeDayWindows`. Each gains an `address player` parameter used for the duplicate
checks, the standing lookup and the slip owner. The burn helpers keep burning from
`msg.sender`: on the paid doors that is the player, on the comp doors it is the vault, and
FLIP's flag decides which ledger pays. `_reserveDay` already takes the player.

Paid doors are unchanged in behaviour: they pass `msg.sender` as the player and the existing
flag set.

### D2. One vault-only comp door, one packed code per comp

`vaultComp(uint256 code) external returns (uint256 charged)`, gated `msg.sender == VAULT`.
The code packs everything the door needs above the recipient's address:

| bits | field |
| --- | --- |
| 0..159 | the player comped, never zero |
| 160..167 | kind: 0 one of today's windows · 1 today's whole day · 2 future days · 3 day upgrade · 4 banked passes |
| 168 | high: the day's multiple on a window or day, the high lane on future days and passes |
| 176..199 | arg: the window's period 0..6 (kind 0), the first day (kind 2), the ticket's day (kind 3) |
| 200..207 | count: days (kind 2) or passes (kind 4); the period mask, bits 0..6, for an upgrade |

Rulings folded in during the build: a comp names no chips (the seat starts blank and the
player re-spreads it with `amendSlip`); comps reach scheduled windows only, so there is no
custom-battle slot and no multiple, only the high flag; `arg` and `count` stay separate
because a run of future days needs a first day and a length.

**Kind 5, a window on days ahead (added 2026-09-05).** The period rides in bits 208..215 of
the code; `arg` is the first day and `count` how many consecutive days. A scheduled window's
field is now keyed by its SLOT rather than a hash of its terms (its terms are a pure
function of the day's word, one set per slot, so the hash added nothing but blindness before
the word), which makes a reservation an ordinary seat placed early: the same entrant counter,
the same one-seat map, the same high count, a blank slip at `(slot << 64) | seat`, nothing
burned. `_openWindow` ORs the stake echo into a field that may already hold seats. A claim
bit in the player's day-seat word stops a later day ticket from folding a second seat into
the reserved window; window entries read only the seat-number bits, so other windows stay
open to the holder. The price is fixed at grant, as future days are: the class's expected
seat from the preset table, times the expected high multiple of nineteen for a high seat.
Indexer note: `battleKey` in scheduled-window events is now the slot number.

| period class | expected seat |
| --- | ---: |
| opener (period 0) | 2,433 FLIP |
| routine (periods 1..5) | 1,227 FLIP |
| tail (period 6) | 14,235 FLIP |

A reserved window bars the holder from a second seat in that window and from a day ticket on
that day; a day ticket bars a reservation. Lapses are not refunded: the crank opens every
day (user ruling). `vaultComp` keeps only the reverts that guard state (user ruling).

Every kind ORs the comp bit into the burn it already makes, so the debit is the very
statement the paid door charges:

| kind | path | debit |
| --- | --- | --- |
| WINDOW | `_enterWindow(_joinableWindow(period), 0, high ? H : 1, to, COMP)` | (bankroll + bounty) × multiple |
| DAY | `_enterToday(0, high ? H : 1, to, COMP)`, which returns the cost | sum of the seven windows × multiple |
| FUTURE_DAYS | burn count × fixed price with COMP, then `_reserveRun(startDay, count, high, 0, 0, to)` | 25,000 / 450,000 per day |
| UPGRADE | `_upgradeDayWindows(to, day, mask, comp = true)` | Σ (bankroll + bounty) × (H − 1) over new bits |
| PASSES | `_credit(to, high, count)` then burn `banked × value` with COMP | 22,800 / 433,200 per pass actually banked |

- PASSES charges only what `_credit` actually banked; a saturated lane is never billed.
- Recipient zero and an unknown kind revert `BadCompRequest`; a shut window, an occupied
  day, a full pass lane and an insufficient comp lane all revert through the existing errors.
  Nothing is silently skipped.
- Existing boons on an upgraded seat are untouched: the comp burn returns a zero mask and
  the upgrade path never writes the boon bits.
- The seat that completes a field is charged `_FINAL_UNITS` (6) on top of its settlement
  cost for the accrual's call into FLIP; `_scoreBattle` reports finalization to `_resolve`.

### D3. Vault

- `crapsComp(uint256[] calldata codes)` `onlyVaultOwner`: one transaction, any number of
  comps, each forwarded to `vaultComp` and logged as `CrapsCompGranted(operator, to, kind,
  charged)`. An empty batch reverts `Insufficient`; a zero recipient reverts `ZeroAddress`;
  any item the table refuses reverts the whole batch.
- Allowances (added 2026-09-05): `setCrapsCompAllowance(who, amount)` lets the owner give an
  address a FLIP-wei budget; that address may then call `crapsComp` and is charged what the
  table charged, all or nothing. The owner's own grants draw on no allowance. Zero revokes.
- `crapsGrantComps`, `CrapsCompsGranted` and `crapsCompsRemaining` are removed. The
  `uint16` was the last field in the salvage slot, so removing it shifts nothing.
- `crapsEnterBattle` (the vault's own seat) keeps paying from the general allowance.

### D4. Events

The ordinary placement, reservation, upgrade and credit events fire as they do for a paid
seat, naming the recipient. The funding mode is visible through FLIP's `CrapsCompSpent`. The
`burned` field of `CrapsDayWindowsUpgraded` names the charge in either mode; document it as
"charged", not "burned".

## Sequence and review gates

1. Phase A on its own branch of work: build, differential parity, full craps suites, sizes and
   gas reported. Nothing economic moves. This is reviewable alone.
2. Phase B and C together: the lane, the accrual, the accrual oracle. Report the reserve bump
   and the finalization gas delta.
3. Phase D: the doors, the vault forwarder, the parity tests (comp seat versus paid seat for
   every kind: owner, standing, chips, counters, high flags, settlement, payout).
4. Repository gates: `make test-foundry`, `make test-hardhat` plus `npm run test:stat`, the
   storage layout oracle, the bytecode manifest, Slither on the changed files, and the
   `check-*` source gates. Record the final size table.

Budget expectation after Phase A: about 3,300 bytes free. Phase C spends roughly 150. Phase
D is the unknown; estimate 400–800 for the threading plus one door. Target at least 1,000
bytes free at the end, measured on a clean tree with the pinned build.

## Decisions taken

- One comp door, one packed code per comp, an array of codes on the Vault (user ruling).
- No chips on a comp, no custom-battle comps, a high flag instead of a multiple (user ruling).
- The vault's own custom-battle seats keep paying from the general allowance.
- Packed-board engine ABI: the scatter runs inside the engine; nine scalars cross the call.

## What this plan does not do

No payout module, no shared storage base, no optimizer change, no delegatecall router, no
owner-settable price or refill, no changes to the boost books or any existing payout. It
authorizes no contract edit by itself; every `contracts/*.sol` change goes to the user as a
diff before it is committed.
